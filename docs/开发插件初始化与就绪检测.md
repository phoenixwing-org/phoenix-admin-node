# 开发插件初始化与就绪检测

## 边界

Hub 的 `mounted` 只证明 Node/Vue 开发源码已挂载，不代表插件已经由 Phoenix 插件中心登记、安装、启用或物化到 Ribbon。Phoenix Admin Node 是 manifest、DDL、迁移台账、菜单贡献和权限的唯一权威；Vue 只展示服务端结论并触发已有受控生命周期。`Pah*` 仅保留为内部类型、表和历史实现前缀，不应出现在面向管理员的页面文案中。

Host 不从产品源码目录直接登记 manifest。管理员必须选择当前产品生成的不可变 `.phoenix.cool` 包；安装器先校验包身份、manifest v2、integrity 清单、迁移 SHA 和 Node/Vue payload。开发 symlink 只在 `NODE_ENV=local` 且双端 payload 与包内字节完全一致时可复用；正式环境仍只接受 Host 管理的普通目录。

## 检测接口

`GET /admin/phoenix/plugin/development-status` 合并以下证据：

- Node/Vue 开发 symlink 是否指向同一个 clean Git 产品 payload；
- Pah 安装记录、manifest 版本与生命周期状态；
- manifest 迁移与 applied ledger 的差集；
- `pah_plugin_menu_contribution` 与实际 Cool 菜单是否一一存在；
- 稳定 `plugin:<moduleId>:<navigationModuleId>` 分组 assignment 是否存在；
- 当前用户实际获授的可见路由；
- API 启动时写入的快照是否已加载当前版本和激活收据。

返回的就绪状态是幂等的：

| 状态 | 含义 | 下一步 |
| --- | --- | --- |
| `mounted-unregistered` | 已挂载，Pah 无记录 | 优先恢复 Host 已保留的匹配包；没有时选择不可变包 |
| `mounted-version-mismatch` | 挂载 manifest 与台账版本不同 | 优先恢复 Host 已保留的挂载版本包；没有时受控重登记 |
| `registered-not-installed` | 已验证/登记，未完成安装 | dry-run 后受控安装 |
| `installed-not-enabled` | 已安装或已停用 | 受控启用 |
| `enabled-contributions-missing` | 菜单、路由或 assignment 缺失 | 停用→启用受控重物化 |
| `enabled-restart-required` | 台账和贡献已就绪，当前进程尚未加载 | 在 Hub 重启 API/Web |
| `enabled-permission-filtered` | Ribbon 已物化，当前角色未授予全部路由 | 管理员配置角色权限 |
| `ready` | 挂载、台账、贡献、权限和启动快照一致 | 无 |
| `quarantined` | 挂载、身份或完整性不可信 | 修复产品包/挂载，不执行生命周期 |

接口不返回产品本机绝对路径，也不调用 Hub 的装配 API。

## 受控初始化

1. `POST /admin/phoenix/plugin/package` 权威验包，并将运行 payload 与包逐文件、逐字节一致的本地挂载记为 development activation candidate。本地源码可额外保留 Host 明确排除出制品的测试/fixture 文件；任何额外运行文件仍 fail-closed。通过完整校验的原始包同时进入 Admin 应用数据目录下的不可变包仓，按 `moduleId/version/SHA-256` 保存，包与元数据权限均为 `0600`。
2. `GET /admin/phoenix/plugin/migration-plan` 生成短时、一次性 dry-run。
3. `POST /admin/phoenix/plugin/local-controlled-install` 在有 pending DDL 时强制创建 `pg_dump` 备份并完成 `pg_restore` 演练，校验备份证明后才在单一事务执行 SQL 和写 ledger；无迁移也经过同一状态机。
4. `POST /admin/phoenix/plugin/enable` 物化菜单、capability 和 Ribbon 投影。首次 assignment 统一进入 Host 内置“业务”分组；已有管理员 assignment 不被覆盖，Host 不自动创建产品大组。
5. `activationMode=restart` 时，界面只打开 Hub，不跨域伪造重启成功。Hub 完成受控重启后，再用检测接口确认新进程快照。

### 开发 watch 的续跑顺序

开发模式下，更新 `src/entities.plugin.ts` 会触发 Midway watch 重启。权威验包流程必须先把
`verified` 安装记录持久化，再同步实体清单；这样即使当前 HTTP 请求被进程重启中断，重启后的巡检仍能
从 `registered-not-installed` 继续，而不会只留下 activation candidate、反复回到“未登记”。

实体同步器还应保证最终内容幂等，不得因为内容相同而重复改写生成文件。后续若继续做逐插件 TypeScript
隔离检查，应在临时编译上下文完成，不能为了检查在 live `entities.plugin.ts` 之间来回切换。

### 开发命令收口

开发挂载的长期入口优先采用 Host-owned CLI，前端不复制生命周期逻辑。目标命令为：

```text
Terminal 1（插件仓）
目录：<plugin-product-root>
命令：<插件仓已审计的 release-package 命令>

Terminal 2（Admin Node）
目录：<phoenix-admin-node-root>
命令：pnpm phoenix:plugin:init <moduleId>
```

页面只显示精确目录、可复制命令、状态和最近一次结果；路径来自本机挂载登记，不写入公开文档或 tracked
配置。CLI 必须复用本节既有权威接口与状态机，不允许插件向 Host 注入任意命令、参数、cwd 或环境变量。
它需要覆盖 `status / init / uninstall`，并满足：

- `init` 可在 watch 重启后幂等续跑，依次完成验包、登记、运行制品检查、dry-run、备份/恢复演练、迁移、字典和贡献物化；
- `uninstall` 默认保留业务数据、migration/dictionary ledger、管理员 assignment 和 Host 包仓原始包；开发 symlink 只撤销活动状态，不删除；
- 任一数据库写操作仍要求非默认隔离数据库、`PAH_DB_SYNCHRONIZE=false`、`PAH_DB_INITIALIZE=false`；
- CLI 和页面使用同一 Node 服务，不形成第二套台账或判断逻辑。

CLI 尚未落地前，可以直接调用相同的 Host 管理接口完成开发初始化；不得用手工 SQL、手改 ledger 或复制
菜单记录代替。

## Host 插件包仓与恢复

- 包仓属于 Admin Host，不属于 Hub，也不使用开发者的 `/Users/.../phoenix.cool` 归档目录；运行时根目录为 `~/.cool-admin/<app-hash>/phoenix-plugin/packages/`。
- development activation candidate 只表示“本次已验证、可激活”的短期候选；Node/Vue payload 是运行装配；原始 `.phoenix.cool` 包仓是三者之外的长期恢复来源，不能互相冒充。
- 停用、卸载并保留数据，以及 `local-package-discard` 撤销本次候选/装配时，均不删除已保留的原始包。删除包仓内容必须是以后单独设计、明确授权的清理动作。
- `GET /admin/phoenix/plugin/development-status` 只返回包名、版本、SHA、大小、源码提交和是否匹配当前挂载，不暴露本机绝对路径。
- 当前挂载与保留包的版本和 `sourceCommit` 一致时，页面显示“使用已上传包继续启用”；`POST /admin/phoenix/plugin/retained-package/restore` 按精确 SHA 读取原始包并重新执行完整权威验包，然后才恢复登记和 activation candidate。它不会跳过 dry-run、安装、启用或重启门禁。
- 包文件、元数据缺失、被替换、为 symlink、大小或 SHA 不一致时一律 fail-closed；不得回退为信任现有 payload 或旧 candidate JSON。

禁止启用 TypeORM `synchronize` / Host `initialize`，禁止直接建表或伪造 applied ledger，禁止把产品 ID、源码路径或分组映射写进 Host tracked tree。

## 2026-09-02 Open Issue 开发挂载实证

`phoenix-open-issue@0.7.2` 在专用数据库完成了一次完整开发挂载初始化：

- 首次恢复保留包时，实体清单写入触发 watch，暴露出“先同步实体、后登记”会留下半成品；Host 已调整为先登记再同步，并补回归测试；
- 运行制品检查报告 2 条迁移、2 条待应用；受控安装创建可信备份并完成真实恢复演练后应用 2/2；
- 字典 dry-run 无冲突，新增 7 类、37 项；插件最终为 `enabled`；
- 数据库实证为 9/9 业务表、2/2 applied migration、32 条菜单贡献；
- 浏览器刷新后出现“业务”Ribbon，以及仪表盘、问题列表、推送历史、8D 报告和功能入口；
  `/open-issue/lists` 冷深链可访问，刷新后的浏览器 warning/error 为 0。

该实证证明开发源码挂载与插件贡献生命周期可以分离：运行代码来自 symlink，Manifest、DDL、字典、权限、
菜单和 Ribbon 仍由同版本不可变包的权威证据驱动，安装过程不会覆盖开发源码。
